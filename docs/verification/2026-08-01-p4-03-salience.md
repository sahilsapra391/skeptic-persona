# p4-03 — Salience curation, measured (2026-08-01)

The acceptance gate for this chunk is a replay against real production data,
not a claim. `scripts/replay-salience.mjs` scores every card production
actually created and reports what the queue would have looked like.

## What the queue actually is (remote D1, 2026-07-27 .. 08-01)

Measured before designing anything. **The plan's premise was wrong**, and the
correction is the point of this record.

| | measured |
|---|---|
| Cards created | 918 over 5 weekdays = **181/day** (7.2x the 25/day target) |
| True approvals | **20 lifetime = 2.18%** (queue.state ∪ post_log; see integrity note) |
| Approvals in the last 3 full days | **0**, against 488 cards |
| Delivered to Telegram | 917 of 918 — the owner really received ~180/day |

**Reg SHO is not the flood.** The plan named per-ticker Reg SHO spam as the
mechanical noise to digest first. It is **12 of 918 cards (1.3%), ~4/day**,
one distinct ticker per card, zero same-day repeats — the baseline day
correctly logged all 56 names and only diffs card afterwards. Digesting it
recovers ~4 cards out of ~181. Worse, `diff.exited` is never persisted
(regsho.ts inserts only `entered`), so the "nightly joins/leaves" card the
plan asks for **cannot be built from stored data** without an ingester
change. Not attempted here.

**The real flood is four mechanical sub-classes inside otherwise good sources:**

| class | volume | approvals |
|---|---|---|
| 8-K item 5.02 (officer/director changes) | 83 of ~106 post-gate cards | 0 |
| HALT volatility pauses (LUDP + M) | 191 of 219 cards | 2 |
| 13D/G amendments | 64 of 86 cards | 0 |
| Form 144 under $5M | 95 of 157 cards | 4 |

Data-integrity finding, recorded because it corrupts any approval metric read
naively: **18 `post_log` rows have `queue.state='expired'`.** No shipped code
path can do that (`expirePendingBefore` filters `state='pending'`; migration
0010 additionally requires `skeleton_id IS NULL`, and all 18 have one). An
out-of-band UPDATE reset them. Reading `queue.state` alone undercounts
approvals by 18 and makes six archetypes look uniformly 0%. The replay and
every number above use `state ∪ post_log`.

## The scorer

`src/salience.ts`, pure (no I/O, no clock) so the replay and the live gate
cannot disagree. Score = ordinal category base + magnitude features.

**Bases encode ORDERING only.** The engagement study forbids its own ratios as
coefficients — "ratios transfer directionally, not numerically … treated as a
tie-breaker on ordering, never imported as coefficients". So the file encodes
congress > enforcement > insider > macro > rates as ordinal tiers; the
1.67x/1.13x/0.56x numbers appear nowhere in it. Categories the study could not
measure (halt, recall: n<25) sit mid-tier and are discriminated by magnitude
rather than punished by base — absence of evidence is not evidence of low
value.

**Magnitude reads VERIFIED payload shapes.** Three field names in the first
draft were wrong and would each have silently scored every item at its bare
base; all three are now regression-pinned:

| assumed | actual |
|---|---|
| `items: ["5.02"]` | `items: [{code, title}]` |
| `totals.value` | `totals.buyValue` / `totals.sellValue` |
| `percentOfClass` | `topPercent` |

## Replay result (all 918 cards, floor 45, bypass 80, caps as shipped)

```
Per day: 131.1 today -> 27.0 after curation (target 25, soft)
Reduction: 79.4%
APPROVED-BUT-HELD: 10 of 20
```

The per-day figures moved from an earlier draft (153.0 -> 30.3) for TWO
reasons in the same commit, and review was right that attributing it to one
was misleading:

1. The harness keyed its daily cap counter on the UTC date prefix while the
   live gate keys on the ET calendar day, so they disagreed about which cards
   shared a cap and the old number described behaviour the Worker does not
   have.
2. Four category bases were raised from below-floor to above-floor in the
   same change (MACRO_PRINT 35->55, FED_PRESS 40->50, TREASURY_AUCTION
   38->50, RATE_DECISION 25->50), moving those categories from always-held to
   pushing. All four score 50-70, below CAP_BYPASS_SCORE=80 and outside
   CEILING_EXEMPT, so each binds at the default 2/day cap: at most +8
   cards/day.

The number above is a re-run AFTER both changes, not the pre-raise figure
carried forward.

## What adversarial review found in THIS chunk, before it merged

Ten defects, two CRITICAL, all in the suppression half — which is the correct
place for the risk to concentrate and the reason the review was worth running
on my own work:

1. **CRITICAL — suppression shipped ON, recovery shipped OFF.** The gate runs
   on code defaults from the instant of merge, while `digest_push` was seeded
   `enabled=0` with the only path to enabling it a hand-typed command inside a
   SQL comment. ~80% of items would have been marked `digested` — removed from
   all 15 ingester drains — with no job to surface them. This repo's own
   discipline note argues against exactly this trade. Fixed: the row ships
   enabled, which its own rule permits because the handler lands in this PR
   and its cadence profile ships with it.
2. **CRITICAL — the digest marked a positional prefix, not the rows it listed.**
   `sentIds = held.results.slice(0, lines.length)` while `lines.length` counts
   only rows that RENDERED. Any skipped row shifted the window, so the
   highest-scoring held item could be marked sent without ever appearing in a
   message: invisible to every drain, no card, never re-listed. Held items are
   the one population whose renderability is never checked, because the gate
   now runs BEFORE `renderForQueue`. Fixed: the listed ids are tracked
   explicitly; unrenderable rows are retired with a loud log instead of
   retrying forever.
3. **HIGH — whole categories were unreachable.** MACRO_PRINT (35), FED_PRESS
   (40) and TREASURY_AUCTION (38) have no magnitude branch, so their score was
   their base for every possible payload, all below the floor. CPI, the jobs
   report and every Fed release could never reach the queue. Their ingesters
   already gate hard, so suppressing again double-counted a filter that had
   run. Fixed and pinned by an invariant test over every archetype.
4. Buttons capped below lines, so items 6-12 were shown once and then
   unpromotable forever — breaking the "held is not lost" guarantee this
   document makes. Fixed: one button per listed line.
5. Replay/live day-boundary disagreement (above). 6. `SALIENCE_FLOOR` had no
upper clamp, so `"450"` would hold everything. 7-10. Doc-comment defaults, no
send pacing, an unrenderable group retrying forever, and the owner's
smoke-test endpoint being curated by the layer it exists to verify.

**The false-negative number is stated, not buried.** 10 of 20 historical
approvals would have been held rather than pushed. Three things about it:

1. **19 of those 20 approvals landed inside the ~6-hour window when Approve
   still auto-posted to Threads**, when the owner was approving liberally to
   exercise the pipeline. It is the weakest evidence in the dataset.
2. **Held is not lost.** Every held item appears in that day's digest with a
   one-tap ↑ promote button that re-enters the normal enqueue path
   (`bypassSalience`), producing a card identical to any other.
3. A parameter sweep over floor × bypass × cap scale (16 combinations landing
   in the 20-34/day band) put the false-negative floor at **9-11 across the
   entire band** — it is not a tuning artifact. The residue is sub-$5M Form
   144s and volatility halts: exactly the classes the measurement says are
   noise, that the owner happened to approve during the liberal window.

Two tuning decisions came directly out of the replay rather than from taste:

- **POSITIONING base 32 → 55.** My first pass read CFTC positioning as
  price/tape and buried it; it is 2-of-8 approved locally, the second-best
  rate we have. Two false negatives were purely this error.
- **A cap bypass at 80.** Caps are first-come-first-served within a day
  because a streaming pipeline cannot know what the afternoon holds. Without
  a bypass the replay held five items the owner HAD approved, scoring 60-88,
  purely because weaker items arrived that morning. This implements the
  owner's amendment literally: "if a day produces 30 genuinely high-salience
  items, push them and let the low-salience categories absorb the squeeze."

## Digests

Held items get `items.status = 'digested'` — a new status value, chosen
because `items.status` has no CHECK constraint and all 15 ingester drain
queries filter `status='new'`, so it suppresses an item everywhere with zero
changes to those queries. Deliberately distinct from `'logged'`: logged never
met the bar, digested met it and lost the slot, and only digested rows may be
promoted.

A digest **cannot** live in the `queue` table (`item_id NOT NULL REFERENCES
items(id)`, plus `archetype`/`draft_text NOT NULL`; a sentinel row would be
swept by `expirePendingBefore`, picked up by `runGeneration` and
`deliverCards`, and badged by the webhook). Hence `digest_items` (migration
0044) and a 21:00 ET `digest_push` job — after the US close and after the
post-close EDGAR wave, which alone holds 24% of all cards.

Doctrine, since a digest is published-shaped copy the owner may screenshot:

- Every line is an item's OWN rendered fact line, and `render.ts` welds the
  attribution onto line 0. So each line inherits non-negotiables #1 and #2 by
  construction — no new claim is composed, no LLM is called, no new validator
  is needed.
- The header says what it is: what WE held back today. It never says nothing
  else happened — absence in our lake is not absence in the world.
- Truncation is always announced (`+N more held`). A silently cut list reads
  as complete: the House-PTR bug class.
- Line cap is ours and explicit (12), because `clampText` truncates at 4,096
  silently.

## Not built here, with reasons

- **:00/:30 batching.** Measured and deliberately deferred: minute-of-hour is
  already near-uniform (5-min buckets range 43 to 123), so the humps are job
  cadence, not event timing. Batching changes packaging, not load — and after
  this chunk the load is 30/day. It also carries real hazards worth their own
  chunk: `telegram_message_id IS NULL` is three-way ambiguous so a batch
  sender keyed on it double-sends, and a never-notified row currently expires
  silently on the same clock as a visible one (proven in production: queue
  #328 was created, never delivered, and expired six hours later).
- **Reg SHO joins/leaves digest.** Needs the ingester to persist `exited`
  first; it is 1.3% of volume, so it is not the lever the plan assumed.
