# p5-06 verification: the digest's north-star block

**Verified:** 2026-08-05 UTC against the live `skeptic-wire` D1 database
(`d951177f-e4ab-4b6b-a014-efc7d78d065e`).

The plan: *"Weekly digest gains the north-star block: approval rate
(approvals/cards) and post rate (posts/approvals), trended weekly."*

## 1. What the block will actually say

Run against production with the shipped query, both windows:

```
 current: cards=651  approvals=10 (2%)  manual_posts=0 (0%)  legacy_auto=0
   prior: cards=418  approvals=19 (5%)  manual_posts=0 (0%)  legacy_auto=18
```

So the next digest reports:

```
North star, last 7 days:
  Approval rate: 2% — 10 of 651 card(s) (down 47% vs last week, from 19)
  Post rate: 0% — 0 of 10 approval(s)
  Nothing has been published from this window. The Copy button is the
  constraint, not the queue.
```

Two things the owner can act on immediately: card volume grew 418 -> 651 while
approvals fell 19 -> 10, so the flood is getting worse and the approval rate
halved with it.

## 2. The counting rule that has already produced a wrong finding once

Approvals are `queue.state IN ('approved','edited')` **UNION** an existing
`post_log` row. Counting state alone loses every card that went on to post,
because such a card no longer carries the `approved` state. PR #115 recorded
what that cost:

> queue.state='approved' 2 / rows in post_log 18 / union 20 of 920 = 2.17%
>
> Counting one column gives 0.22% pipeline-wide and makes press look like the
> only category converting.

The prior window above is that same shape in live data: **19 approvals, of
which 18 are only visible through `post_log`.** State-only counting would have
reported 1.

`edited` counts as an approval for the same reason `deliverCards` treats it as
one: it is approved-with-changes, not a rejection.

## 3. The exclusion that matters most, and production proves it

The 18 Threads-era posts are AUTOMATED, published by the parked auto-poster
before the ban, to a platform the desk no longer publishes to. They are counted
and named, and they never enter the post rate.

**The prior window is the proof this was necessary.** Folded in, it would read:

```
  Post rate: 95% — 18 of 19 approval(s) posted
```

A 95% post rate, for a desk whose owner has published **zero** posts by hand.
That is the exact silent-success shape `rag/digest.ts` was written to refuse,
and it would have appeared in the first digest after this chunk shipped.

Excluded and named instead:

```
  18 Threads-era automated post(s) in this cohort are excluded from the post rate.
  They were published by the parked auto-poster, not by the owner, and not to X.
```

## 4. One cohort, not three windows

Cards, approvals and posts are all counted over the SAME cohort: queue rows
created in the window. A post is attributed to the week its card was created,
not the week it was posted, so the funnel card -> approval -> post shares a
denominator. Three separately-windowed counts would let a post from an older
card inflate a quiet week's rate above 100%.

## 5. The guard is the denominator, never the numerator

This is the subtle half, and it is where the file's existing doctrine needed
care rather than copying.

`rag/digest.ts` already refuses to render a zero-edit rate when nothing has
been published, because there is genuinely nothing to measure. **The post rate
is not the same case.** Zero posts against 29 approvals is measured, real, and
the single most important number the program has:

- `cards === 0` -> no approval rate exists. Said as such.
- `approvals === 0` -> nothing could have been posted. Said as such.
- `manualPosts === 0` with approvals > 0 -> **0%, stated plainly**, plus the
  line naming the Copy button as the constraint.

Conflating those would either hide the finding or invent one. Pinned by tests
in both directions.

## 6. Placement: above the zero-edit rate, before the early returns

`renderDigest` returns early when `stats.posted === 0` — which is exactly the
state the north star exists to report. Appended at the end, the block would
have been invisible precisely when it is the only measurable thing in the
digest. It is emitted immediately after the header, before any early return,
and a test pins that it survives the zero-posts branch.

It also leads on merit: the zero-edit rate scores the drafts we produce, the
north star scores whether any of them reach the public.

## 7. Tests

Five added:
- zero posts against real approvals renders a measured `0%`, not a no-data branch
- a zero DENOMINATOR renders no rate at all, and never prints `0%`
- Threads-era automated posts are named and kept out of the rate
- approvals are the state-UNION-post_log figure, driven through a real queue
  row whose state is `pending` but which carries a `post_log` row
- the block survives `renderDigest`'s early returns

Suite: **1,039 passing**, 1 pre-existing failure (D-6, red on main).
